# 后续优化方案

本 PR 先把真实 API 链路、单图隔离、批量并行和证据边界跑通。下一阶段按风险和收益推进：

## P0：真实链路验收

- 使用页面内临时 API Key 完成一次三 Agent 实测，记录 `run_id`、模型请求 ID、每个 Agent 的耗时、token 和失败原因。
- 固化百炼 Responses API 的超时、流式事件和来源字段映射；将上游错误转换为可读的“配置错误 / 超时 / 上游限流 / 返回格式错误”。
- 明确检索服务的生产地址与鉴权方式，禁止在报告中把社交媒体文案自动提升为产品事实。

## P1：批量任务编排

- 为每张图片生成 `run_id` 和 `item_id`，增加取消、重试、并发上限和单项失败后的继续执行。
- 增加批次汇总视图：已完成、需补证、失败、耗时和可导出的逐图结果。
- 对相同图片做哈希去重，避免重复触发视觉识别和检索费用。

## P1：可审计证据链

- 将产品身份、用户声明、官方事实、来源和核验结论统一为带 ID 的证据对象。
- 每条结论保留来源 URL、抓取时间、来源类型和核验状态；报告只引用结构化证据。
- 为“无来源”“来源冲突”“只有 UGC”增加明确的 UI 状态和导出字段。

## P2：性能与可观测性

- 对视觉识别、检索和报告生成分别统计首事件延迟、总耗时、超时率和输出长度。
- 使用缓存、指数退避和预算上限降低重复请求；流式事件增加心跳与断线恢复。
- 日志只保留脱敏后的请求 ID、阶段和错误类型，API Key 始终只存在页面内存。

## 验收补充

- 增加真实上游 smoke test（不提交密钥），覆盖三 Agent 同时成功、单 Agent 超时、畸形 JSON、检索无来源和批量混合成功。
- 浏览器验收覆盖多图上传、单项失败隔离、取消运行、窄屏抽屉和减少动态效果设置。
